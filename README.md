# MosDNS 优选一体机

原版 [mosdns](https://github.com/IrineSistiana/mosdns) 源码构建 + 优选 + 单登录控制台。
零第三方黑盒；运行时不下载任何东西；所有版本可由 `versions.env` 锁定。

## 特性

- **原版核心**：从官方 v5 源码 `go build`，零第三方打包。
- **优选**：Cloudflare / Google 搜索 / Google 翻译 / GitHub / ghcr.io / TMDB / IMDb，串行执行（全局锁，CPU 弱也不怕）。
- **只留最快的一批 + 备胎**：每路先取「延迟不超过最快 1.5 倍」的那一批（最多 N 个），不足保底个数就从池里补历史验证过的备胎——不让任何一路只剩一个 IP，一坏就没得换。
- **多 IP + IPv6**：IPv4 / IPv6 各自排序，一次写入 hosts，某个 IP 失效可自动切换。
- **HTTPS 校验（排除 1034）**：TCP 通不等于可用。对候选逐个发起真实 TLS 握手 + `Host` 请求，**Cloudflare 1034 / 1010 / 1020、证书不符、5xx 一律剔除**，避免优选到一个打开就报错的 IP。
- **自包含**：候选 IP 靠运行时向本机 mosdns 实时解析，延迟靠 TCP 直连探测；工具与种子固化在镜像内，**不存在"拉不下来"**。
- **默认国内优先**：未知域名先走国内 DoH，超时/失败才走国外；GFW 清单强制走国外。
- **IP 归属校验**：国内返回的 IP 必须落在国内网段才采用，被污染则丢弃转国外。
- **诊断页**：IP 查询（境内/境外、CDN 厂商、PTR）、端口连通检测（ICMP + TCP + UDP）、域名查询（A/AAAA + 逐 IP 归属与延迟），**每次都是现查，点「重新查询」即刷新**。
- **消息推送**：企业微信 / 钉钉 / 飞书 机器人 Webhook，可按事件（每轮完成 / 失败或降级 / 登录提醒）推送，只推事件不推明细。
- **清单自更新**：国内 IP 段、CDN 网段库（Cloudflare / Google / Fastly 官方源）都可每日自动更新 / 手动更新，UI 里能看到条目数、更新时间、来源，并支持预览。
- **单登录 UI**：概况 / 监测 / 日志 / 配置 / 源；实时解析域名；亮/暗/系统三态（桌面端在侧边栏「外观设置」里切，手机端在顶栏）；侧边栏底部带退出登录；移动端底栏。
- **数据隔离**：个人运行数据只写 `/data` 卷，镜像与仓库不含任何个人数据。

## 部署

`docker-compose.yml` 就是最小可用配置，**复制即用，不用改任何东西**：

```bash
docker compose up -d
docker logs -f mosdns
```

然后：

1. 浏览器打开 `http://<服务器IP>/` 。
2. 初始账号 **`admin` / `admin`**，登录后**强制要求改掉**（账号名也能一起改），改完才进得去。
3. 忘记密码：删掉 `/data/auth.json` 再重启容器，回到 `admin` / `admin`。

镜像两个来源内容一致，选一个：

```bash
docker pull po9873/mosdns:latest           # Docker Hub
docker pull ghcr.io/po9873/mosdns:latest   # GitHub Container Registry
```

想让容器独占一个局域网 IP（设备上 DNS 直接填它），把 `ports` 去掉，改用 macvlan：

```yaml
    mac_address: <自定义 MAC>          # 可选，方便路由器做静态绑定
    networks:
      <你的 macvlan 网络名>:
        ipv4_address: <你的局域网 IP>

networks:
  <你的 macvlan 网络名>:
    external: true
    name: <你的 macvlan 网络名>
```

> 调优参数（缓存、看门狗间隔、上游 DoH…）**默认都不用写**，
> 见下面「配置项」，或直接进控制台「配置」页改，保存即生效，不用重启容器。

## IP 源（官方 / 第三方 / 镜像，可勾选、可定时扫描）

候选 IP 不再只靠"实时解析 + 内置种子"，而是接了一份**源清单 + 候选池**：

| 类型 | 内容 | 说明 |
|---|---|---|
| 官方 | Cloudflare 官方 v4/v6 网段 · Google 官方网段（`gstatic/ipranges/goog.json`）· GitHub 官方网段（`api.github.com/meta`） | 最权威，但只有网段，按固定步长采样成具体 IP 再探测 |
| 第三方 | IPDB 精选 v4 / v6、IPDB 接口、IPDB 反代优选 | 社区测速后维护，更新快、量小 |
| 镜像 | jsDelivr、ghproxy | 同一份数据，raw.githubusercontent 直连不通时兜底 |
| 自定义 | ① 你自己填的 v4 / v6 地址；② **直接粘贴 IP 清单** | 两种都支持：给地址就定时去拉，贴清单就直接进池（不走网络） |

每一路都有源，且不只是官方源：官方源给的是「全量网段」，社区 hosts 源给的是「当前真能用的前端 IP」，
两者互补——官方网段采样展开后能连上的很少（GitHub 实测 60 个候选只选出 1 个 IP），
社区清单直接就是 IP 清单，补位快得多。

| 路 | 官方源 | 其他源 | 网段数（实测） |
|---|---|---|---|
| Cloudflare | `cloudflare.com/ips-v4` + `ips-v6` | IPDB 精选 / IPDB 接口 / IPDB 反代优选 / jsDelivr 镜像 / ghproxy 镜像 | v4 15 段 / v6 7 段 |
| Google 搜索 | `gstatic.com/ipranges/goog.json` | GitHub 网段镜像（每日转文本）/ jsDelivr 镜像 / **社区实测 IP 清单（Ponderfly）** | v4 132 段 / v6 16 段 + 8819 个实测 IP |
| Google 翻译 | 同上（同一份数据） | 同上 | v4 132 段 / v6 16 段 + 8819 个实测 IP |
| GitHub 访问 | `api.github.com/meta` | GitHub520 社区 hosts（HelloGitHub）/ ineo6 hosts（GitLab）/ jsDelivr 镜像 | v4 254 段 / v6 6 段 |
| ghcr | `api.github.com/meta`（**默认关**：几万条段里随机采样命中率约 0.8%，扫不出来） | 准确入口清单写在 `config/seeds/ghcr.txt`（10 个，实测逐个打过 TLS + `GET /v2/`） | v4 254 段 / v6 6 段 |
| TMDB | AWS 官方 `ip-ranges.amazonaws.com/ip-ranges.json`，**只取 `service=CLOUDFRONT`** | 无 | v4 214 段 / v6 34 段 |
| IMDb | 同上（同一份数据，单独一条） | 无 | v4 214 段 / v6 34 段 |

### 每一路到底给哪些域名写 hosts

控制台「概况」卡片和「结果」页会把这些域名逐个列出来（不用猜），对应如下：

| 路 | 写进 hosts 的域名 |
|---|---|
| Cloudflare | `cloudflare.com`、`theaudiodb.com`、`www.theaudiodb.com`、`lrclib.net`、`anilist.co`、`graphql.anilist.co` |
| Google 搜索 | `www.google.com`、`www.google.com.hk`、`google.com` |
| Google 翻译 | `translate.google.com`、`translate.googleapis.com` |
| GitHub 访问 | `github.com` |
| ghcr | `ghcr.io`、`pkg-containers.githubusercontent.com`、`raw.githubusercontent.com`、`objects.githubusercontent.com` |
| TMDB | `www.themoviedb.org`、`api.tmdb.org`、`api.themoviedb.org`、`image.tmdb.org` |
| IMDb | `www.imdb.com`、`m.media-amazon.com` |

同一路里的域名是「同一批边缘节点」才合并的（Cloudflare / CloudFront 各家同家任意域名通用）。
不是一批的绝不共用：`github.com` 和 `raw.githubusercontent.com` 就分在两路、各用各的 IP。
附加域名写之前会逐个 IP 验一遍，验不过这次就不映射，不会让那个域名打不开。

> 社区 hosts 源是「`IP 域名`」格式。**这类清单按域名白名单收**：只保留本路真正用得上的域名那一行，
> 其余行（别的站点、assets、Pages）整行跳过——以前整份照收，池子里一半 IP 根本不属于这一路
> （实测 GitHub 池里混进过 Facebook、微软的地址），优选时抽到的全是「TCP 通但这域名不认」的垃圾。
> 纯 IP 行（没有域名）不受影响。校验仍按该路自己的目标域名做真实 HTTPS，通不过的不进 hosts。

### 手动加源：两种都行

「源」页右上角「+ 添加」：

1. **给清单地址**：填 v4 / v6 地址，选好「喂给哪一路」，添加后立刻拉一次，显示能拿到多少 v4 / v6。
2. **直接粘贴 IP 清单**：选「直接粘贴 IP 清单」，把 IP 贴进去就行（纯 IP、网段 `1.2.3.0/24`、hosts 格式
   `1.2.3.4 github.com` 都认）。不走网络，保存即入池——源拉不到、或者你从别处拿到几个能用的地址时，用这个兜。

两种都要选「喂给哪一路」：拉到的 IP 只进那一池，只服务那个域名。

> 候选不只来自订阅源。每轮优选结束会把 **DNS 实时解析到的 IP**、**种子兜底 IP**、**通过 HTTPS 校验的 IP** 都回填进该路候选池，
> 控制台每张池子卡片下面的「来源明细」**逐源列出名字和数量**（比如 CF 池：IPDB 精选 66 / Cloudflare 官方网段 62 / IPDB 接口 15 …），
> 一眼能看出这一池子的数到底是谁给的，而不是只有一个笼统的「共 N 个」或「订阅 / 解析 / 种子」三个大类。

## 源的定时体检（官方 + 第三方都查）

| 项 | 说明 |
|---|---|
| 频率 | 默认每天 05:00 一次（`源` 页可开关，也可点「立即体检」） |
| 查什么 | 所有源**包括已停用的第三方源**，逐个拉一次，只看能不能拿到 IP；不写池 |
| 官方源失败 | 只标红，不自动停用——它是权威定义，多半只是临时断网 |
| 第三方/镜像失败 | **拉不到就删**（默认失败 1 次即删，`PREF_SRC_DISABLE_AFTER` 可调大以容忍抖动）；源列表里不留废源，也**不再标红**；把它带来的、还没验证过的 IP 从候选池一并带走（实测能通的保留） |
| 恢复 | 删掉的**内置源**点「恢复内置源」一键补回；「失效自动删除」开关关掉则改为只停用 |
| 通知 | 有源失效时推一条 `warn` 消息（企微 / 钉钉 / 飞书） |

体检和「定时拉取」「扫描新源」是三件不同的事：

- **定时拉取**：把启用中的源拉一遍，新 IP 进池（增量更新候选）
- **源体检**：复检所有源的连通性，发现挂掉的源（含一直正常的，防止突然失效没人知道）
- **扫描新源**：只测「还没测过 / 上次失败」的源，把能用的纳进来（默认关闭）

每个源都显示 **v4 N 段 ≈X 个 · v6 M 段 ≈Y 个**，勾选框决定是否参与拉取和优选，取消勾选立即停用。

**定时扫描**（`源` 页可配）：默认每 6 小时把启用源拉一遍，拉下来的 IP 去重后进候选池；同时清理失效 IP（已拉黑、连续失败、14 天没再出现、超出上限）。不拉就会越来越少可用，所以这一步是自动的。

**源订阅**：一行一个清单地址，同步进来的源默认**不启用**，勾上才参与。支持两种格式：

```
[{ "name": "某社区镜像", "url_v4": "https://.../v4.txt", "url_v6": "https://.../v6.txt" }]
```
```
某社区镜像 | https://.../v4.txt | https://.../v6.txt
```

`GitHub 加速前缀` 可用于把 `raw.githubusercontent.com` 的地址改写成加速地址（如 `https://ghfast.top`）。

## 1034 一出现就换 IP（不是只显示出来）

分两层，缺一不可：

| 层 | 触发时机 | 行为 |
|---|---|---|
| 优选时校验 | 每轮优选 | 真实 TLS + `Host` 请求，识别 1034/1010/1020、证书不符、5xx；命中就**立即**从当前 hosts 摘掉并重载，不等本轮跑完 |
| 看门狗巡检 | 默认每 180 秒 | 对**正在生效**的 IP 再校验一遍，发现 1034 就换掉，并从候选池补一个通过校验的进来 |

关键点：

- 被 1034/证书/5xx 拒绝的 IP 写进黑名单，冷却 `PREF_BAD_TTL_HOURS`（默认 6 小时）内不再使用
- **绝不降级使用坏 IP**：如果候选全被拒绝，宁可撤下该路 hosts（域名回退上游解析），也不会把 1034 的 IP 写进去
- 只有「超时/连不上」才允许降级，并标记 `unverified`；连续 3 次连不上同样会被换掉（避免误杀网络抖动）
- 每次换 IP 都写一条记录，控制台「源 → 换 IP 记录」能看到：哪个 IP、什么原因、换成了哪个
- 结果展示前还会再过滤一道：`/api/results` 遇到 `cf1034` / `cert` / `http5xx` 直接剔除，
  并在卡片上写「已剔除 N 个（cf1034）」。所以这些 IP **不会**出现在「优选 IP」里，
  只会在剔除说明里出现

概况页的每个路由卡片会**逐行列出所有优选 IP**：左边 IP、右边延迟和下载吞吐，
两列各自对齐（IPv6 不折行、数值不用挤在 IP 后面）。
每个卡片左边还会列出这一路服务的全部域名，**每行两个**——十来个域名一行一个会把卡片拉得老长。

概况页顶部三栏里，「上游 DNS（引擎正在用）」每行右侧标着**这是哪家的**
（阿里 DNS / 腾讯 DNSPod / Cloudflare / ControlD …，按主机名和落地 IP 认，
认不出来就留空，不编厂商名），下面的「上次扫描」一行写候选池总数和可用数。

## 分流清单（国内 IP 段会变）

`china_ip.txt` 是「国内 IP 归属检测」的依据，随 APNIC 分配每月都在变，所以做了三层：

| 层 | 做法 |
|---|---|
| 构建时 | CI 从多个公开源下载完整清单固化进镜像（失败则用仓库内置种子） |
| 运行时 | 默认每 24 小时检查一次，过期才下载；多源依次尝试，任一成功即原子替换 |
| 兜底 | 全部源失败 → **保留旧清单**，只在 UI 标记「更新失败」，绝不会把清单弄空 |

列表来源（依次尝试）：`17mon/china_ip_list` → `ispip.clang.cn` → `china-operator-ip` → APNIC 官方委派记录（自动把 `1.0.1.0/256` 转成 `1.0.1.0/24`）。

**在哪里看**：控制台「源」页 → 分流清单表（条目数 / 大小 / 更新时间 / 来源 / 状态），点「预览」看前 40 行，点「更新」立即拉取。概况页顶部也有一条 `国内 IP 段 7,456 条 · 2 小时前`。

**什么时候生效**：mosdns 不监听清单文件变化，所以更新后需要重载进程（约 1 秒）。程序会自动做，也可以点「重载引擎」。

## 关于重启（重要）

mosdns 没有热重载接口，改 hosts / 清单只能重启进程。为了不打扰使用：

- **一轮跑完只判断一次**，绝不「每路重启一次」；
- 本轮结果与上轮**完全一致时直接跳过重启**（IP 通常几天不变，所以大多数轮次是 0 次重启）；
- 清单更新与优选结果合并到同一次重载，不会连着重启两次；
- 重启由 supervisor 接管，中断约 1 秒；
- 不想自动重启可在「配置」页关掉「结果变化后自动重载引擎」，改为手动点「重载引擎」。

## 更新

- 上游自动探测：每周一（可在 workflow 改 cron）。
- 服务器升级：`docker compose pull && docker compose up -d`。
- 回退：`docker pull ghcr.io/<user>/mosdns:<旧tag>` 后改 compose 的 image 即可。

## 登录账号

固定初始 **admin / admin**，不再支持用环境变量指定（避免密码写在 compose 里）。

首次登录会被**强制改密**：前端不给进控制台，后端除了登录/改密/状态以外的接口一律返回 403，
所以绕过页面直接调接口也进不去。改完密码后才会放行。

忘记密码：删掉 `/data/auth.json` 再重启容器，会回到 admin / admin 并再次强制改密。

## 定时任务（全部在「配置 → 定时任务」里改，保存即生效，不用重启）

| 任务 | 默认 | 说明 |
|---|---|---|
| 优选 | 每 60 分钟 | 一轮跑完后的等待时间；可整体暂停 |
| 国内 IP 段更新 | 每 24 小时 | 拉最新网段，失败保留旧清单 |
| 源定时拉取 | 每 6 小时 | 把启用的源拉一遍，补候选池 |
| 源定时体检 | 每天 05:00 | 复检所有源还能不能用；非官方源连续失败到阈值会被删 |
| 源自动发现 | 关闭 / 每天 04:00 | 自己找新的公开源并试一遍 |
| 上游 DoH 扫描 | 每 60 分钟 | 把候选池全测一遍：新变得可用的收进来，在用的死了自动换（手动模式下只提示、不动配置） |
| 生效 IP 巡检 | 每 180 秒 | 正在用的 IP 触发 1034 / 证书不符 / 5xx 立即撤下换 IP |

间隔（分钟/小时/秒）、周期（1~12 小时 / 每天 / 每周）、几点执行（0~23 点）都能改，
每行右边显示「上次 / 下次」实际时间。只有缓存上限和日志轮转属于引擎启动参数，需要改环境变量后重启。

## 配置项（环境变量）

| 变量 | 默认 | 说明 |
|---|---|---|
| `PREF_UI_PORT` | `80` | 控制台端口 |
| `PREF_DNS_PORT` | `53` | DNS 端口 |
| `PREF_STABLE_HOURS` | `6` | 优选稳定窗口（小时）：窗口内当前 IP **能打开且不慢** 就跳过全量重探；0 = 每轮都重扫 |
| `PREF_STABLE_TTFB_MS` | `1200` | 慢到什么程度就换：真实 HTTPS 响应时间超过这个值（ms）就重新优选 |
| `PREF_STABLE_SPEED_KBPS` | `200` | 吞吐下限（KB/s）：实测下载低于它也算变慢；0 = 不看吞吐 |
| `PREF_THREADS` | 空 | 优选并发；空=自动（CPU/虚拟化自适应） |
| `PREF_CACHE_SIZE` | `8192` | DNS 缓存条数上限（LRU 淘汰，超出自动丢最旧的） |
| `PREF_WATCHDOG_SEC` | `180` | 换 IP 看门狗巡检间隔的**初始值**；登录后在「配置 → 定时任务」里改，立即生效 |
| `PREF_BAD_TTL_HOURS` | `6` | 坏 IP 冷却时长（小时） |
| `PREF_POOL_MAX` | `4000` | 候选池上限 |
| `PREF_SUB_TTL_DAYS` | `14` | 多少天没再出现就清理 |
| `PREF_CIDR_SAMPLE` | `6` | 官方网段每个 CIDR 采样几个 IP |
| `PREF_SRC_DISABLE_AFTER` | `1` | 非官方源失败几次就处理（默认 1 次，怕抖动可调 2~3） |
| `PREF_SRC_AUTO_DELETE` | `1` | 到阈值直接删除源（`0` = 只停用保留） |

> **上游 DoH 不再写死任何厂商**：容器启动时在【本地】逐个探测候选清单，只把"当地真能通"的写进配置。
> 这样换网络/换环境无需改代码，探测不到就如实报"无可用上游"。

## 自定义上游 DoH（检测源可更新）

国外/国内上游都来自两份**可编辑的检测源清单**，镜像只负责在文件缺失时补齐默认版，**绝不覆盖你改过的版本**：

| 文件 | 用途 |
|---|---|
| `/data/doh_remote_candidates.txt` | 国外 DoH 候选（强制走国外解析时使用） |
| `/data/doh_local_candidates.txt` | 国内 DoH 候选（国内域名解析） |

每行格式：`<DoH地址> [连接 IP]`，`#` 开头为注释。例如：

```
https://dns.controld.com/dns-query 76.76.2.2
https://dns.nextdns.io/dns-query 45.90.28.1
```

- `连接 IP` 可选：让 TLS 的 SNI 仍用域名、但实际连这个 IP（mosdns 的 `dial_addr`），避免再解析上游域名造成自循环；同时跳过证书校验（裸 IP / 自签必然对不上）。
- 探测与运行时用同一种方式（POST + `application/dns-message`）验证，并要求返回 `rcode=0` 且有答案，避免"HTTP 200 但其实解析不了"的假可用。
- **怎么加自己的**：把能用的自建/代理 DoH 地址加进对应文件、重启容器即可，探测会自动把它纳入。
- 处于带 SNI 嗅探的网络时，已知 DoH 主机名（cloudflare-dns.com 等）会被拦，此时加一个不在黑名单里的地址即可。

### 控制台里改上游：先测，再写

「配置 → 上游 DNS」里填的每一条，保存前都会**真连一遍**（TLS 握手 + 实际发一次 DNS 查询，
校验 `rcode=0` 且有答案）。有不通的就不写进配置，逐条列出原因（连不上 / 超时 / HTTP 非 200 /
REFUSED / 查不到记录），要强制写入还得再确认一次——避免一条死掉的上游把「控制台一切正常、
但全网解析随机失败」这种最难查的故障带进来。

「仅测试」只测不存；「扫描候选池」立刻跑一轮定时扫描；手动模式下扫描发现的新可用会显示成
「补入 N 条」，点一下才会加进你的清单（加之前再复测一遍，只补这次仍然通的）。

下面还有一个可展开的**候选池明细**，把整池每一条都列出来：绿点＝在用，橙点＝探测通过但没启用
（带「加入」，点一下加到上面的清单，仍要走「测试并保存」），红点＝连不上并附实际错误
（`timed out` / `Connection refused` / `reset by peer` / `HTTP 非 200` / 查不到记录）。
表头直接给「在用 N 条 · 可用未启用 N 条 · 不通 N 条」——「试了 26 条只通 5 条」和
「只找到 1 条」是两件事，这个区别必须看得见。

> 实测参考：在一条对国际 DoH 双向阻断的网络里，26 条国外候选只有 ControlD 的
> `76.76.2.0~.3` 四个 anycast 和 `doh.dns.sb` 能通，其余（Cloudflare / Google / Quad9 /
> OpenDNS / AdGuard / NextDNS / Mullvad / DNS.SB 主站）全部超时或 reset。
> 所以同一家服务的多个入口都留在池子里是有意义的：换的是入口，不是服务。

### 定时扫描：上游是活的

DoH 上游会变——今天被阻断的明天可能通了，今天能用的明天可能挂掉。所以候选池每
`doh_scan_min`（默认 60 分钟）全测一遍：

| 模式 | 扫描发现 | 行为 |
|---|---|---|
| 自动（没手动配过） | 在用的失效 / 有更快的 | 自动换成最快的可用项并热重载，只留 `doh_keep`（默认 3）条 |
| 手动（控制台存过） | 有新的可用 | 一条都不动，只记下来给界面提示，点「补入」才写入 |

细节：

- 候选池 = `/data` 里的用户清单 **+** 镜像内置清单，升级带来的新候选会自动并入 `/data`（按**整行**去重），
  保证「定时扫描用的池子」和「重启后启动探测用的池子」是同一份。按整行而不是按 URL，是因为
  同一服务常有多个 anycast 入口，按 URL 去重会把备用入口全吃掉、只剩一条能试。
- 选路分两轮：先保证「不同服务各取最快一条」（多样性），还不够 `doh_keep` 条再用同一服务的
  其它入口补（冗余）。一个 provider 有多条入口同时挂着，某条路由被掐时不用等下一轮扫描。
- 正在用的那几条也参加探测：仍通就**原样保留**（连 `dial_addr` 一起），不会每轮换一遍、也不会把
  bootstrap IP 洗掉；一条都不通时这侧不动（多半是整网断了，不能因为一次扫描失败就把上游清空）。
- 扫描器带文件锁和限频，没到点立刻返回；挂在 watchdog 的常驻线程里跑，不占优选主循环。
- 失败原因（超时 / REFUSED / HTTP 非 200）会写进 `pref.log`，界面上也能看到每条的延迟或错误。

## 「监测」页：上游此刻多快、域名能不能打开

这两件事都只认 mosdns 自己的答案，不另找工具。

**上游当前速度**：整池里**每一条**上游各开一个只指向它的 mosdns 入口
（`127.0.0.1:16001` 起 local、`16061` 起 remote），然后问它一次真实的 DNS 查询，量耗时。
不是只测「正在用的那三条」——要用的是「都有哪些上游、各自多快」，只列在用的等于把其余全藏了。
为什么不能从外部直连 DoH：外部探测有自己的连接、自己的并发、自己的超时，
而 mosdns 这边有连接复用和并发取最快，两条路径测出来的数不是一回事。
页面每 60 秒自动测一遍：绿 ≤300ms、黄 ≤1000ms、红 更慢；打不开的不画速度条，标「不通」并写出真实原因。

**国内、国外各自一个框**：两边是两套独立的选路，混在一列里看不出谁替谁。
每行写「厂商 + 域名 + IP」（阿里 DNS / 腾讯 DNSPod / Cloudflare / ControlD …，
认不出来的就只写域名，不编一个像厂商的名字），在用的那条带「在用」标签。

**域名能不能打开**：解析只问 `127.0.0.1:53`（就是 mosdns 的分流结果，用户实际拿到的 IP），
然后对每个 IP 真发一次 HTTPS 请求（SNI 与 Host 都是这个域名），用与优选同一套判定
（状态码 / 1034 / 证书 / 5xx），得出「能正常打开 / 一个都打不开」。
TCP 握手成功不算数——握手成功但打不开的情况太常见，那才是最难查的故障。

> 入口由 `entrypoint` 在渲染配置时自动生成，上游变了会跟着重建；
> 端口只用环回，不对外暴露。

## 判定「能用」看什么：不用 TCP 延时，用真实响应 + 速度

一个 IP「TCP 能连上」不等于能用——Cloudflare 1034、证书错、源站 5xx 全是 **握手成功但页面打不开**。
所以每次校验都发真实 HTTPS 请求（SNI 和 Host 都用目标域名），量两个数：

- **响应**：从发起连接到收到响应首字节的时间（TTFB，含 TCP + TLS + 请求 + 后端处理）
- **吞吐**：接着读响应体估下载速度（KB/s）。响应体小于 4KB 时不显示（样本太小没意义）

界面上的 `275ms` 就是 TTFB，`· 8.4 MB/s` 是吞吐（拿得到才显示）。

**每一路「什么算能用」不一样，按路指定**（`scheduler/*_pref.sh` 里的 `PREF_PROBE_*`）：

| 路 | 请求什么 | 判定 |
|---|---|---|
| Cloudflare / GitHub / ghcr | `GET /` | HTTP 正常、无 1034/证书错/5xx |
| Google 搜索 | `GET /`（www.google.com） | 正文出现 `<title>Google` |
| Google 翻译 | `GET /`（translate.google.com） | 正文出现 `translate`（该页是纯 JS 壳，没有 `<title>`） |

为什么不用「状态码通就算」：Google 前端对不认识的路径一律回 404/200 的空壳，
只看状态码会把「能连但不能用」的节点全当成好的（`203.208.x` 那批就是这样被误判的）。

### 吞吐前面的 `≈` 是什么意思

`≈158 KB/s` 表示 **样本太小、只是个大概值**：响应体不足 32KB，一个 TCP 窗口就传完了，
算出来的 KB/s 抖动极大（同一个 IP 同一个地址实测能出 158 / 289 / 532 三种结果）。

所以这种估算值**只用来给你看个大概，不参与「是不是变慢了」的判断**——
否则每轮都会被几十 KB 的样本判成「慢」，白跑三分钟全量重探。真正判决用的是
「响应时间」和「可信吞吐样本（≥32KB）」两个；而且每个在用的 IP 会连测两次取更好的那次，
只要有一次证明它不慢，就不折腾它。

### 会遇到的失败原因（不只 1034）

| 标记 | 含义 |
|---|---|
| `CF 1034` | Cloudflare 无法解析源站（回源失败），这个 IP 用不了 |
| `CF 1016` / `1020` / `1015` / `1023` | 源站 DNS 找不到 / 被防火墙拒 / 限速 / 主机不可达 |
| `CF 10xx`（其他） | Cloudflare 节点侧的其他错误，同样视为不可用 |
| `证书错` | 证书不匹配或过期：被劫持、或 SNI 与 IP 不属于同一站点 |
| `HTTP 5xx` | 源站或中间层 5xx（500/502/503/504），服务端故障 |
| `超时` | 连接或响应超时（网络抖动，允许降级但标「未校验」） |
| `连不上` | 连接被重置 / TLS 握手失败 |

**明确坏**（1034/证书/5xx）→ 立刻拉黑并换 IP；**只是超时**→ 降级用但标「未校验」，
绝不把坏 IP 当好的写进 hosts。

## 每路留几个 IP：只留最快的一批，但绝不止一个

选结果分两步（配置页可调「每路保留 IP 数」和「每路最少保留」）：

1. **只留最快的那批**：先看这一路最快的那个，延迟不超过它 **1.5 倍**的才算「这批」，最多留 N 个
   （默认 3）。慢一拍的不占位置——各路一个标准，不是只有 GitHub 这么干。
2. **不够就补备胎**：这批不足「最少保留」（默认 3）时，从候选池里挑**历史上真验证通过过**的
   IP 补上，标成「备胎」。备胎本轮不复测、不加减分，主力坏掉时守护进程会先拿它顶上。

为什么非要保底：ghcr.io 这种路，证书只挂在极少数地址上——扫遍 Azure 的 `20.27.176~178`
（762 个地址）只有 `20.27.177.117` 认这个域名；GitHub 自己的 `140.82.112.0/20` 里也只有
每个 /24 的 **第 33、34 号地址**带 `*.ghcr.io` 证书（`.3` / `.42` 那些才是 `github.com`）。
一轮下来天然只选得出 1~2 个。只剩一个 IP 时它一抖，整路立刻没得换，只能干等下一轮重扫
（几分钟）。留两个备胎，切换是秒级的。

> 顺带一个教训：别用「整段扫一遍全是 cert」来判断一个网段没用。`140.82.112.0/20` 随机采样
> 会得出「全是 github.com 证书」的结论，实际上 4096 个地址里有 8 个是 ghcr.io 的入口——
> 采样点没落到 `.33/.34` 上而已。这类入口的准确清单放在 `config/seeds/ghcr.txt`，
> 而且**种子里的 IP 会无条件进校验环节**，不会因为池子里那些「TCP 秒回、却根本不提供该服务」
> 的采样候选排序更靠前就被挤掉。

## TMDB / IMDb 两路是怎么回事

这两站整站（网页 / API / 海报）都在 **AWS CloudFront** 上，而 CloudFront 是一张 anycast 大网：
随便哪个边缘 IP，只要证书对，就能服务任何 CloudFront 站点（实测 `99.84.215.46` 同时能开
themoviedb、api.tmdb、imdb、image.tmdb）。所以做法是——从 AWS 官方 `ip-ranges.json` 里
**只取 `service=CLOUDFRONT`**（214 段 v4 / 34 段 v6），采样展开成本机候选，挨个实测，
挑最快的写进 hosts。找对一个快的边缘 = 这两站都快。

两个坑：

- **不能拿官方全量清单**：那份 JSON 里 90% 以上是 EC2 / S3 / AMAZON 段（6000 多条），
  全塞进池子只会把候选稀释掉，抽到的大多不是边缘节点。按 `service` 过滤后才是干净的。
- **不能按页面正文判定**：`www.themoviedb.org` 根路径回 **403 + Cloudflare 挑战页**，
  `www.imdb.com` 回 **202 + 反爬页**，正文里有没有站点名全看对方心情——批量探的时候
  同一批 IP 单测能过、连测就判「不提供该服务」，误杀一大片。这两路只认**证书 + 有响应**：
  CloudFront 对「不认识这个域名」的请求在 TLS 阶段就用默认证书（`*.cloudfront.net`）应答，
  我们的证书校验根本过不去，能过就说明这个地址确实承载了这个站点。

另外 `ghcr.io` 路会**单独**再写一行镜像层域名 `pkg-containers.githubusercontent.com`
（走 Fastly，`185.199.10x.154`）。只映射 `ghcr.io` 的话，`docker pull` 会卡在拉层那一步——
认证和 manifest 走 ghcr.io，镜像层数据走的是另一个域名、另一批节点。

## 优选稳定模式（不每次全跑）

默认 `stable_hours=6`。每轮不是上来就全量扫，而是先问一句「现在这些 IP 还能用、还不慢吗」：

1. 对当前选中的 IP 各发**两次**真实 HTTPS 请求（就是上面那两项：响应 / 吞吐），取更好的那次；
2. **全部打不开**（1034 / 证书 / 5xx / 超时）→ 先交给守护进程换 IP，**连续两轮**都全打不开才全量重探
   （单轮偶发抖动很常见，不能一抖就白跑三分钟）；
3. **能打开但变慢**（响应 > `stable_ttfb_ms`（默认 1200ms），或**可信的**吞吐样本 < `stable_speed_kbps`（默认 200KB/s））→ 重探；
4. **能打开且不慢** → 完事，什么都不动，`stable_hours` 内不再全量扫。

为什么每项测两次：单次吞吐抖动大（同一 IP 实测 158/289/532 KB/s），一次就判「慢」会天天误触发；
只要两次里有一次证明它不慢，就不算慢。为什么 `≈` 的估算值不参与：样本只有几十 KB 时算出来的
KB/s 是噪音，拿来判决只会让系统一直折腾。

多源（订阅/种子）在这里的角色是**切换依据**，不是每轮都全量重扫。

### Google 两路为什么必须用「社区实测清单」

这是个容易搞反的地方，写清楚免得以后再走弯路：

- **Google 官方网段（`goog.json` 里的 142.250.x 等）在国内基本连不上**：实测 TCP 443 全部超时。
  所以「从官方网段采样再探」这条路，永远探不出能用的 IP——不是判定太严，是那些地址真连不上。
- **但 Google 搜索和翻译在国内确实还有可用 IP**，它们是一批国内边缘节点（8.134/8.137/8.138、
  113.31、106.75、47.113 等）。官方网段里没有这些地址，社区工具
  [Ponderfly/GoogleTranslateIpCheck](https://github.com/Ponderfly/GoogleTranslateIpCheck)
  每天实测后把清单提交进仓库，本项目直接把它当源用（可更新，不写死）。
- 清单只提供**候选**：能不能用仍由本机实测决定，探不通的不进 hosts。

校验这两个域名时还有两个坑，代码里都处理了：

1. **必须带 ALPN**。握手不带 ALPN 时，对端会按「默认虚拟主机」应答，回一张不相干域名的证书
   （实测 `CN=yaoqianmeiyong.site`），看着像「证书不对」，其实浏览器用得好好的。
2. **不能拿翻译接口做校验**。`translate_a/single` 无 key 有配额，优选一轮要探几十个 IP，
   探着探着自己就被 429 限速，于是所有节点都「失败」——等于自己把判据打爆了。
   现在按「首页 + 页面特征」判断：翻译首页是纯 JS 壳，看 `translate` 字样；搜索首页看 `<title>Google`。

### 整层不通的路会自己「歇着」（失败退避）

有的路在当地是整层不通的（个别地区/网络到某批 IP 完全不可达），全量探测每轮都要白跑 2~3 分钟，
最后还是「TCP 探测全部失败」。这种情况没必要反复折腾——域名走上游解析照常能用。

- 连续失败 → 退避 **1h → 2h → 4h → 6h（封顶）**，期间不再空跑，日志写「暂停优选」
- 一旦选出结果 → 退避立即清零
- 点「立即测试」= `PREF_FORCE=1`，**忽略退避立刻真跑**（你说了算）
- 界面显示「已暂停优选」并说明原因，不会让你以为坏了

## 缓存与日志（不会无限增长）

- **DNS 缓存**：`cache` 插件按条数上限做 LRU 淘汰（默认 8192 条，`PREF_CACHE_SIZE` 可调），
  不会因为长期运行而无限变大；缓存同时落盘到 `/data/cache.dump`，重启可复用。
- **一键清空**：控制台「概况 → 缓存与日志」里可看到当前条数 / 上限 / 占比 / 累计命中 / 落盘体积 / 日志体积，
  点「清空 DNS 缓存」立即释放（同时删掉落盘副本，避免重启又被加载回来）。
- **实时解析域名**：读取 mosdns `query_summary` 日志（时间/域名/类型/命中缓存/用时/状态/客户端），
  每 5 秒自动刷新，可在同一张卡里手动输入域名现查。
- **查询日志**：超过 32MB 自动只保留尾部 8MB，也可在控制台手动清空。

## 目录

```
config/       mosdns 配置模板 + 公开种子（cn/gfw 清单、优选候选种子）
scheduler/    调度 + 优选 + 公共函数 + DNS/探测/清单库（lib/lists.py）
ui/           控制台后端(server.py) + 前端(static/index.html)
versions.env  上游版本锁定
known-good.env 最后一份通过自检的组合
docker-entrypoint.sh  渲染配置 / 种入账号 / 拉起三进程
```

## 隐私

仓库只含通用代码、配置模板与公开种子；优选结果、域名数据、账号密码全部只在你的 `/data` 卷，永不进镜像或 GitHub。

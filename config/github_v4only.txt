# 只发 IPv4 的域名（AAAA 一律返回 NODATA）
#
# 背景：GitHub 的资源域走 Fastly，其 v6 段 2606:50c0::/32 在服务端/容器侧探测
# 可通，国内客户端侧却被连接重置。优选出来的 hosts 只写 A 记录，AAAA 查询会穿过
# hosts 走上游拿回真 v6，于是支持 v6 的设备优先选 v6 → 卡死。
# docker pull ghcr 的典型表现：ghcr.io 正常拿到 IPv4，真正下载镜像层的
# pkg-containers.githubusercontent.com 拿到 v6，下到一半 connection reset。
#
# 这里列的是「这个网络里走 v6 一定坏」的域，不是「没有 v6」的域：
# github.com / api.github.com 本来就是纯 v4，列上只是让规则更完整、少一次上游查询。
# 新增域时确认一遍：它在 v6 上是不是真的不可用，别把能用的 v6 也关掉。

domain:github.com
domain:githubusercontent.com
domain:githubassets.com
domain:github.io
domain:ghcr.io

# ---- 翻译族 ----
# 同 ghcr 的病，但更隐蔽：优选 hosts 只写 A 记录，而 settings.json 里 ipv6=true，
# 客户端（Chrome / Windows / 手机）按 RFC 6724 会优先连 AAAA 拿到的 v6。
# 日志里 translate.googleapis.com / clients5.google.com / translate-pa 的 qtype 28
# 都返回 rcode 0（真的拿到了 v6），这些 v6 在国内连不通；Happy Eyeballs 有时回退
# v4 成功、有时不回退，表现就是「翻译一时能用一时不能用」，而守护只探 IPv4 的
# 优选 IP，永远报「一切正常」。和 ghcr 一样：在 DNS 层直接把 AAAA 判成 NODATA。
# 静态资源域一并列入：它们同样被优选 pin 成 IPv4，漏 AAAA 会拖垮整页翻译脚本加载。
domain:translate.google.com
domain:translate.googleapis.com
domain:translate.googleusercontent.com
domain:translate-pa.googleapis.com
domain:translation.googleapis.com
domain:clients5.google.com
domain:clients6.google.com
domain:www.gstatic.com
domain:fonts.gstatic.com
domain:ssl.gstatic.com

# ---- Docker Hub 族 ----
# 上游给 docker.io 的 AAAA 是随机投毒段(2a03:2880::/32 等)，客户端按 RFC 6724
# 会优先连 v6 然后超时/重置；和 ghcr 一样，DNS 层直接判 NODATA 强制走 v4。
domain:docker.io
domain:docker.com
